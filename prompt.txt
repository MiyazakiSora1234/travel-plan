現在の旅行計画アプリに「旅行計画の更新機能」を追加してください。

前提：
- frontend と backend が既に存在する
- mobile も存在するが、今回はまず frontend を中心に実装する
- 既存の旅行計画登録機能は動作している
- 旅行計画一覧画面も存在する
- 既存の設計・命名規則・APIクライアント・バリデーションを可能な限り再利用する
- 勝手に別アーキテクチャへ変更しない
- 既存機能を壊さないことを最優先する
- TypeScript の型安全性を維持する
- React Hook Form + Zod + MUI を利用している
- API層は既存の apiClient / shared API 定義を優先して利用する

# ゴール

以下のユーザー操作を実現する。

旅行計画一覧
    ↓
旅行計画を選択
    ↓
旅行計画編集画面
    ↓
既存データがフォームに表示される
    ↓
内容を変更
    ↓
「更新する」
    ↓
PUT/PATCH API
    ↓
更新成功
    ↓
旅行計画一覧へ戻る
    ↓
更新された内容が表示される

また、既存の旅行計画登録画面についても、
「新規登録」と「更新」でフォームコンポーネントを共通化する。

--------------------------------------------------

いきなり実装を開始しない。

最初に以下を調査する。

- frontend のディレクトリ構成
- routing
- 旅行計画一覧画面
- 旅行計画登録画面
- TripCreateForm
- tripCreateSchema
- API client
- trips API
- Trip 型
- React Query / TanStack Query の利用状況
- エラーハンドリング
- loading 状態
- snackbar / toast 等の通知方式
- backend の Trip Controller
- backend の Trip Service / UseCase
- backend の Repository
- backend の DTO
- 更新APIが既に存在するか
- HTTPメソッドが PUT / PATCH のどちらなのか
- mobile 側に同様の実装があるか

まず現在の設計を理解してから実装すること。

--------------------------------------------------
# 2. API設計
--------------------------------------------------

既に旅行計画更新APIが存在する場合は、それを利用する。

存在しない場合は backend に更新APIを追加する。

基本的には以下を想定する。

PUT /api/v1/trips/{id}

Request:

{
  "name": "東京・京都旅行",
  "startDate": "2026-09-01",
  "endDate": "2026-09-05",
  "memo": "ホテル予約済み"
}

Response は既存APIのレスポンス形式に合わせる。

重要：

- APIのレスポンス形式を既存APIと統一する
- frontendだけ独自形式を作らない
- DTOを適切に定義する
- IDはURL Path Parameter
- 更新対象のIDをRequest Bodyに重複して持たせない
- 存在しないIDの場合は404
- 不正な入力は400系
- サーバーエラーは既存のエラーハンドリング方針に従う

--------------------------------------------------
# 3. frontendのフォーム設計
--------------------------------------------------

現在の TripCreateForm を確認し、
新規登録専用フォームになっている場合はリファクタリングする。

理想構成：

TripForm
    ├── 新規登録
    └── 更新

例えば：

components/trips/TripForm.tsx

props：

interface TripFormProps {
  defaultValues?: TripFormValues
  onSubmit: (values: TripFormValues) => void
  isSubmitting: boolean
  submitLabel?: string
}

ただし、既存プロジェクトの設計により適切な形がある場合はそちらを優先する。

重要なのは、

「登録フォーム」と「更新フォーム」で同じ入力UIを二重実装しないこと。

共通化するもの：

- 旅行名
- 開始日
- 終了日
- メモ
- Zod validation
- エラー表示
- MUI TextField
- ボタン
- loading状態

画面ごとに変更するもの：

新規登録：
- 初期値は空
- 「登録する」
- POST

更新：
- APIから取得した既存データを初期値として設定
- 「更新する」
- PUT/PATCH

--------------------------------------------------
# 4. 新規登録画面
--------------------------------------------------

既存の登録画面を壊さない。

例えば：

/trips/new

など、既存routingに合わせる。

表示：

旅行計画を作成

[旅行名]
[開始日] [終了日]
[メモ]

[キャンセル] [登録する]

登録成功後：

旅行計画一覧へ遷移する。

--------------------------------------------------
# 5. 更新画面
--------------------------------------------------

以下のようなURL設計を基本とする。

/trips/:id/edit

例：

/trips/123/edit

画面表示：

旅行計画を編集

[旅行名]
[開始日] [終了日]
[メモ]

[キャンセル] [更新する]

画面表示時に GET API を実行して既存データを取得する。

例：

GET /api/v1/trips/123

取得後、

reset({
  name: trip.name,
  startDate: trip.startDate,
  endDate: trip.endDate,
  memo: trip.memo,
})

のように React Hook Form に設定する。

重要：

useForm の defaultValues に非同期APIの結果を直接入れようとしない。

API取得後に reset() を利用する。

--------------------------------------------------
# 6. 一覧画面から編集へ遷移
--------------------------------------------------

旅行計画一覧の各カード/行に、

「編集」

ボタンまたは編集アイコンを追加する。

例：

東京・京都旅行
2026/09/01 - 2026/09/05
ホテル予約済み

[編集]

「編集」を押すと、

/trips/:id/edit

へ遷移する。

カード全体クリックではなく、
編集操作は明示的なボタンとして実装する。

アクセシビリティも考慮する。

--------------------------------------------------
# 7. 更新成功後
--------------------------------------------------

更新API成功後：

1. 成功通知
2. 一覧画面へ遷移
3. 一覧データを最新状態にする

React Query / TanStack Query を利用している場合は、

queryClient.invalidateQueries({
  queryKey: ...
})

を利用する。

ブラウザをリロードしないと一覧が更新されないような実装は禁止。

既存のqueryKey設計に合わせる。

--------------------------------------------------
# 8. React Queryを利用している場合
--------------------------------------------------

既存プロジェクトがTanStack Queryを利用している場合、

以下のように責務を分離する。

useTrip(id)
useCreateTrip()
useUpdateTrip(id)

など。

例：

const updateTripMutation = useMutation({
  mutationFn: (values) => updateTrip(id, values),
  onSuccess: async () => {
    await queryClient.invalidateQueries({
      queryKey: ['trips'],
    })

    navigate('/trips')
  },
})

ただし、既存のqueryKey設計を確認して統一する。

API呼び出しをReactコンポーネントへ直接大量に書かない。

--------------------------------------------------
# 9. エラー処理
--------------------------------------------------

以下を必ず考慮する。

- IDが不正
- IDの旅行計画が存在しない
- API通信失敗
- バリデーションエラー
- 更新中の二重送信
- ネットワーク切断
- サーバーエラー

特に更新ボタンは、

disabled={isSubmitting}

などで二重送信を防止する。

取得中：

「読み込み中...」

取得失敗：

「旅行計画の取得に失敗しました」

404：

「旅行計画が見つかりません」

など、ユーザーが状態を理解できるUIにする。

--------------------------------------------------
# 10. backendの更新処理
--------------------------------------------------

backend側に更新APIが存在しない場合は追加する。

既存のアーキテクチャを確認して、

Controller
    ↓
UseCase / Service
    ↓
Repository
    ↓
Database

という責務分離を維持する。

ControllerにDB処理を書くなどの実装は禁止。

例：

TripController
    ↓
UpdateTripUseCase
    ↓
TripRepository
    ↓
PostgreSQL

既存のCreate処理などと設計思想を統一する。

--------------------------------------------------
# 11. 更新時のバリデーション
--------------------------------------------------

frontendだけでなくbackendでも必ず検証する。

frontend：

Zod

backend：

既存のBean Validation等

最低限：

- name 必須
- name 最大100文字
- startDate 必須
- endDate 必須
- startDate <= endDate
- memo 最大2000文字

frontendのvalidationだけを信頼してはいけない。

--------------------------------------------------
# 12. セキュリティ
--------------------------------------------------

以下を確認する。

- URLのidをそのまま信用しない
- backend側で存在確認
- 将来的な認証追加を考慮した設計
- 他ユーザーのTripを更新できる設計にしない
- SQL Injectionを発生させない
- SQLを文字列連結しない
- frontendから送られた値を無条件に信用しない

現時点で認証がない場合でも、

「認証が追加されたら所有者チェックをどこに入れるか」

を意識した設計にする。

--------------------------------------------------
# 13. mobileとの共通化
--------------------------------------------------

frontendとmobileで既に共有API層が存在する場合は、
可能な限り共通化する。

ただし、Web専用UIとMobile専用UIは無理に共通化しない。

共通化対象：

- API型
- Trip型
- API request / response型
- validation schema
- API endpoint定義
- business logic

共通化しない：

- MUIコンポーネント
- React Nativeコンポーネント
- navigation UI
- Web専用レイアウト

既存のshared構成を確認して適切に配置する。

# 16. テスト
--------------------------------------------------

最低限以下をテストする。

Frontend：

- フォームが表示される
- 既存データがフォームにセットされる
- バリデーションが動く
- 更新ボタンでAPIが呼ばれる
- 更新成功後に一覧へ遷移する
- APIエラー時にエラー表示される
- 二重送信できない

Backend：

- 正常更新
- 存在しないID
- 不正な入力
- startDate > endDate
- nameの最大長
- memoの最大長

既存テストの方式に合わせる。

--------------------------------------------------
# 17. アンチパターン
--------------------------------------------------

以下は禁止。

- TripCreateFormとTripUpdateFormに同じフォームUIをコピペする
- Reactコンポーネントからfetch/axiosを直接大量に呼ぶ
- ControllerにDB処理を書く
- frontendだけでvalidationする
- 更新後にwindow.location.reload()する
- 更新成功後に一覧データを手動で適当に書き換える
- URLのidをnumberに変換しただけで存在確認したつもりになる
- APIレスポンス型をanyにする
- `as any` でTypeScriptエラーを隠す
- `useEffect`を大量に使って状態管理する
- API取得前にundefinedの値を無理やりフォームへ渡す
- 新規登録と更新で別々のvalidation schemaをコピペする

# 20. 最重要
--------------------------------------------------

実装前に必ず既存コードを読み、
「現在のプロジェクトで既に採用されている設計」を優先すること。

勝手に新しいライブラリを追加しない。

既存のAPI client、React Query、routing、validation、error handling、shared packageなどがある場合は、それらを利用する。

今回の目的は単に「更新できるようにする」ことではなく、

「新規登録と更新でフォームを再利用でき、
一覧 → 編集 → 更新 → 一覧という自然なCRUD構造を持ち、
将来的に削除・詳細表示・認証・権限管理を追加しても破綻しない構成」

にすることである。

実装後、

1. 変更したファイル一覧
2. 各ファイルの変更理由
3. API仕様
4. 画面遷移
5. 共通化した部分
6. backendの変更点
7. テスト結果
8. 今後の拡張ポイント
9. 残っている技術的負債

を最後に報告してください。
