あなたはシニアDevOpsエンジニア兼テックリードです。

現在のプロジェクトに、GitHub Actionsを利用したEC2への自動デプロイ（CI/CD）を実装してください。

# 前提

このプロジェクトは以下の構成です。

* Frontend: React + TypeScript + Vite
* Backend: Spring Boot + Java + Gradle
* Database: PostgreSQL
* Frontend / Backend / PostgreSQL はDocker Composeで管理
* 本番環境はAWS EC2
* GitHubをソースコード管理に使用
* Dockerを前提とする
* 将来的にRDS / ECS等へ移行する可能性があるため、EC2依存の設計にしすぎない
* 現在はまずEC2 + Docker Composeでシンプルかつ堅牢なCI/CDを構築する

# 目的

GitHubのmainブランチにpushされたら、

1. GitHub Actionsが起動
2. Frontendのテスト・ビルドを実行
3. Backendのテストを実行
4. Backend / FrontendのDocker Imageをビルド
5. GitHub Container Registry（GHCR）へImageをPush
6. GitHub ActionsからSSHでEC2へ接続
7. EC2上で対象Imageをpull
8. Docker Composeでコンテナを更新
9. BackendのHealth Checkを実行
10. 正常ならデプロイ成功
11. 異常ならデプロイ失敗として終了

という流れにしてください。

# 重要な設計方針

## 1. EC2上でビルドしない

EC2では以下を実行しないでください。

* npm install
* npm run build
* ./gradlew build
* docker build

ビルドはGitHub Actions側で完結させます。

EC2は基本的に、

* Docker Imageをpull
* コンテナを起動
* Health Check

だけを担当します。

## 2. Docker Imageを成果物として扱う

GitHub Actionsで作成したImageには、必ずGit commit SHAをタグとして付けてください。

例:

ghcr.io/OWNER/REPOSITORY/backend:${GITHUB_SHA}
ghcr.io/OWNER/REPOSITORY/frontend:${GITHUB_SHA}

`latest`だけに依存する設計は禁止します。

理由は、ロールバック可能なデプロイにするためです。

## 3. secretsをハードコードしない

以下をソースコードに直接書かないでください。

* EC2のIP
* SSH秘密鍵
* DBパスワード
* GHCR認証情報
* API Secret
* AWS Secret

GitHub ActionsではGitHub Secretsを使用してください。

想定するSecret:

* EC2_HOST
* EC2_USER
* EC2_SSH_KEY

GHCRについては、可能ならGitHub Actions標準のGITHUB_TOKENを利用してください。

## 4. 本番.envをGit管理しない

EC2上に本番用.envを配置する方式にしてください。

例:

/opt/travel-plan/.env

このファイルはGitHub Actionsから上書きしないでください。

DB接続情報などの本番環境固有値はEC2側で管理します。

## 5. Docker Composeを本番用に分離

現在のcompose.ymlを確認してください。

開発環境と本番環境で設定が異なる場合、

compose.yml
compose.prod.yml

のように分離してください。

本番用ComposeではImageを直接指定できる構成にしてください。

例えば、

services:
backend:
image: ghcr.io/OWNER/REPOSITORY/backend:${IMAGE_TAG}

frontend:
image: ghcr.io/OWNER/REPOSITORY/frontend:${IMAGE_TAG}

のような形式です。

実際のリポジトリ名・Image名は既存プロジェクトを調査して適切に設定してください。

# GitHub Actionsファイル

以下を作成してください。

.github/
└── workflows/
└── deploy.yml

ただし、既存のGitHub Actionsが存在する場合は、まず内容を確認し、重複するworkflowを作らないでください。

# Workflowの構成

deploy.ymlは以下のような段階構成にしてください。

## Job 1: test

Frontend:

* npm ci
* lint
* test
* build

Backend:

* ./gradlew test
* ./gradlew build

ただし、既存のpackage.json / build.gradleを確認して、実際に存在するnpm scriptやGradle taskだけを使用してください。

存在しないコマンドを勝手に追加しないでください。

## Job 2: build-and-push

test成功後に実行。

* GHCR login
* Backend Docker Image build
* Frontend Docker Image build
* Git SHAタグ付与
* GHCRへPush

可能ならDocker Buildx + GitHub Actions Cacheを使用して、ビルド時間を短縮してください。

## Job 3: deploy

build-and-push成功後に実行。

SSHでEC2へ接続し、

cd /opt/travel-plan

へ移動。

その後、

IMAGE_TAG=${GITHUB_SHA}

を利用して、

docker compose -f compose.prod.yml pull
docker compose -f compose.prod.yml up -d

を実行してください。

ただし、既存コンテナやCompose構成を確認してから具体的なコマンドを決定してください。

# Health Check

デプロイ後、BackendのHealth Checkを必ず実行してください。

Spring Boot Actuatorが既に存在するなら、

/actuator/health

を利用してください。

存在しない場合は、必要最小限のActuator設定を追加してください。

Health Checkは、

* コンテナが起動した
* HTTPレスポンスが正常
* BackendがUP

を確認できるようにしてください。

単にdocker compose up -dが成功しただけでデプロイ成功扱いにしないでください。

# ロールバック

可能なら、デプロイ前のIMAGE_TAGを取得しておき、

新しいImageのHealth Checkが失敗した場合、

直前のImageへ戻す仕組みを実装してください。

ただし、ロールバック処理が複雑になりすぎる場合は無理に実装せず、

「現在のバージョンを記録する」
「失敗時に旧IMAGE_TAGでdocker compose up -dできる」

ところまで実装してください。

勝手に危険な自動ロールバック処理を作らないでください。

# セキュリティ

以下を必ず確認してください。

* SSH秘密鍵をログに出力しない
* GitHub Secretsをechoしない
* .envをGitHub Actionsへ転送しない
* DBパスワードをWorkflowへ直接書かない
* EC2のDocker daemonを外部公開しない
* PostgreSQLを0.0.0.0:5432でインターネット公開しない
* SSHは可能ならSecurity Groupで接続元を制限できる設計にする
* GHCR Imageをprivate repositoryとして扱える構成を検討する

# Docker

既存のDockerfileを必ず確認してください。

以下を勝手に作り直さないでください。

* Dockerfile
* compose.yml
* Spring Boot設定
* React設定

既存構成に問題がある場合は、まず問題点を説明し、CI/CDに必要な最小限の変更だけ実施してください。

Frontendは本番環境ではVite開発サーバーではなく、可能なら、

React build
↓
Nginx
↓
静的ファイル配信

というマルチステージDocker Imageにしてください。

ただし、既存構成を確認した上で実装してください。

# ブランチ戦略

現在のプロジェクトのブランチ構成を確認してください。

基本的には、

main
↓
production deploy

とします。

featureブランチではproduction deployを実行しないでください。

必要なら、

pull_request:
branches:
- main

でテストだけ実行するworkflowを別途作成してください。

# 失敗時の挙動

以下の場合はデプロイしないでください。

* Frontend test failure
* Backend test failure
* Docker build failure
* Docker push failure

つまり、

Test
↓ 成功
Build
↓ 成功
Push
↓ 成功
Deploy

という依存関係にしてください。
