# 旅行計画アプリ 共通化リファクタリング実装指示

あなたは、React / React Native / TypeScript / TanStack Query / Spring Boot / Javaに精通したシニアソフトウェアエンジニア兼アーキテクトです。

既存の旅行計画アプリに対して、**frontend（Web）とmobile（React Native）の重複コードを整理し、今後の機能追加でも保守コストが増えにくい構成へリファクタリングしてください。**

単純なコピペ削除ではなく、

* 責務分離
* 依存方向
* 再利用性
* 型安全性
* テスト容易性
* 将来の機能追加
* Web / Mobile双方の独立性

を考慮してください。

---

# 1. 最重要ルール

## 既存機能を壊さない

今回の作業はリファクタリングが目的です。

以下を原則として維持してください。

* API仕様を勝手に変更しない
* URLを変更しない
* HTTP Methodを変更しない
* DB Schemaを変更しない
* 画面仕様を変更しない
* UIデザインを勝手に変更しない
* React Queryの挙動を変更しない
* キャッシュ戦略を勝手に変更しない
* エラーハンドリングを勝手に変更しない
* Backend APIのレスポンス形式を変更しない

「共通化のために仕様を変更する」のは禁止です。

仕様変更が必要になった場合は、そこで作業を停止して報告してください。

# 6. React Queryを共通化

最優先で実施してください。

現在frontend/mobileに重複しているReact Query hookを、

```text
shared/query/
```

へ集約してください。

ただし、WebとMobileでAPI Clientの実装が異なる可能性があります。

そのため、

```text
shared
  ↓
API Clientを直接import
```

する構造は禁止します。

Dependency InjectionまたはFactoryを使用してください。

例:

```ts
export const createTripQueries = (tripsApi: TripsApi) => ({
  useTrips: () =>
    useQuery({
      queryKey: ["trips"],
      queryFn: tripsApi.listTrips,
    }),

  useTrip: (id: number) =>
    useQuery({
      queryKey: ["trips", id],
      queryFn: () => tripsApi.getTrip(id),
    }),

  useCreateTrip: () => {
    const queryClient = useQueryClient();

    return useMutation({
      mutationFn: tripsApi.createTrip,
      onSuccess: () => {
        queryClient.invalidateQueries({
          queryKey: ["trips"],
        });
      },
    });
  },
});
```

ただし、既存コードのqueryKey、staleTime、mutation、invalidateQueriesなどを必ず確認し、**既存挙動を維持してください。**

# 7. API Wrapperを共通化

以下のような構造にしてください。

```text
shared/api/trips.ts
```

ここにTrip APIの定義を集約してください。

例:

```ts
export const createTripsClient = (apiClient: ApiClient) => ({
  listTrips: () =>
    apiClient.get<Trip[]>("/trips"),

  getTrip: (id: number) =>
    apiClient.get<Trip>(`/trips/${id}`),

  createTrip: (request: CreateTripRequest) =>
    apiClient.post<Trip>("/trips", request),

  updateTrip: (id: number, request: UpdateTripRequest) =>
    apiClient.put<Trip>(`/trips/${id}`, request),

  deleteTrip: (id: number) =>
    apiClient.delete(`/trips/${id}`),
});
```

これは例です。

**必ず既存API実装を確認し、実際のURL・HTTP Method・Request・Response型を維持してください。**

Web:

```ts
const tripsApi = createTripsClient(apiClient);
```

Mobile:

```ts
const tripsApi = createTripsClient(apiClient);
```

という形を基本とします。

# 9. Backend DTO

Backendについては慎重に扱ってください。

現在、

```text
CreateTripRequest
UpdateTripRequest
```

のフィールド・Validationが完全一致している場合、共通化候補として検討してください。

ただし、

```text
POST
PUT
```

でValidationルールや意味が異なる可能性がある場合は、無理に統合しないでください。

特に、

```text
Createでは必須
Updateでは任意
```

のような仕様差が将来発生する可能性を考慮してください。

### 原則

「コードが似ているから統合」ではなく、

```text
APIとして同じ意味を持つか
```

を基準に判断してください。

# 10. Trip Validation定数

以下のような値が複数箇所に存在する場合、

```text
100
2000
```

などをTripドメインの定数として整理してください。

例:

```java
public final class TripConstraints {

    public static final int NAME_MAX_LENGTH = 100;
    public static final int DESCRIPTION_MAX_LENGTH = 2000;

    private TripConstraints() {
    }
}
```

使用側:

```java
@Size(max = TripConstraints.NAME_MAX_LENGTH)
```

ただし、既存Validation仕様は変更しないでください。

# 13. TripForm

Create / Editでフォーム内容が重複している場合、

```text
TripForm
```

へ切り出してください。

理想:

```text
TripCreatePage
    ↓
TripFormPageLayout
    ↓
TripForm

TripEditPage
    ↓
TripFormPageLayout
    ↓
TripForm
```

TripFormは、

```text

Validation表示
フォーム状態
```

を担当し、

Create / Edit固有の、

```text

初期データ取得
submit後のnavigation
```

などはPage側で管理することを基本としてください。

# 最重要

**既存機能を壊さないことを最優先してください。**

「綺麗なアーキテクチャ」にすることより、

```text
既存仕様維持
↓
重複削減
↓
責務分離
↓
型安全性
↓
テスト
↓
将来拡張
```

の順番を優先してください。

また、共通化できるコードを見つけても、**変更理由が異なるものまで無理に共通化しないでください。**

最終的な判断基準は、

> 「今コードが似ているか」

ではなく、

> **「今後も同じ理由で変更されるコードか」**

としてください。
